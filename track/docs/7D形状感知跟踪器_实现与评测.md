## 二、7D 状态的设计（关键）

### 2.1 状态定义（照搬论文 Eq.1）

```
x = [x, y, ẋ, ẏ, a, r, θ]ᵀ
```

| 分量 | 含义 | 来源 |
|---|---|---|
| `x, y` | 掩膜质心 | 掩膜一阶矩 |
| `ẋ, ẏ` | 质心速度 | 恒速模型 |
| `a` | 掩膜面积（前景像素数） | 掩膜像素和 |
| `r` | 掩膜宽高比（w/h） | 掩膜 bbox |
| `θ` | 掩膜朝向（弧度） | **二阶图像矩** `0.5·atan2(2μ11, μ20−μ02)` |

运动模型：**质心恒速，形状静态**（`F` 只在 `[0,2]`、`[1,3]` 上耦合）。

### 2.2 为什么不用 ultralytics 自带的 KalmanFilterXYAH

自带的滤波器把状态**硬编码**成 8 维 `(x, y, a, h, vx, vy, va, vh)`，`_motion_mat`/`_update_mat` 在
`__init__` 里就定死了。要真正的 7D + 静态形状模型，只有两条路：
（a）fork 整个类；（b）新写一个小而自洽的线性滤波器。

选了 (b)：`ShapeKalmanFilter7D` 只有 `initiate / predict / multi_predict / update` 四个方法，
约 120 行，状态布局与观测矩阵都是显式写出来的，便于核对。

### 2.3 观测矩阵（踩过的坑）

```
H = 5×7，把 [x, y, ẋ, ẏ, a, r, θ] 投影到 [x, y, a, r, θ]
H[0,0]=H[1,1]=H[2,4]=H[3,5]=H[4,6]=1，其余 0
```

> ⚠️ **必须写成 5×7 的显式矩阵**。一开始写成 `np.eye(7)`，结果 `m - projected_mean` 报
> `(5,) vs (7,)` 广播错误 —— 观测是 5 维（没有速度），状态是 7 维，两者不能直接相减。

### 2.4 必须覆盖 `tlwh` / `xywh`（最容易忽略的坑）

基类 `STrack.tlwh` 的实现是：

```python
ret = self.mean[:4].copy(); ret[2] *= ret[3]; ret[:2] -= ret[2:] / 2   # 假定 XYAH
```

它假定 `mean[:4]` 是 `(cx, cy, w, h)`。但 7D 布局里 `mean[2:4]` 是**速度**！
若不覆盖，速度会被当成宽高读出来 → bbox 退化成一条线 → IoU 恒为 0/1 → **跟踪完全失效**
（实测：两帧间只差 2px 的两个框，IoU 距离竟返回 1.0）。

因此重写了两个属性，按面积与宽高比反解 bbox：

```python
h = sqrt(area / aspect);  w = aspect * h     # 由 w*h=area、w/h=aspect 反解
```

### 2.5 掩膜几何提取

`extract_mask_geometry(results, n)` 从 `results.masks.data`（`(N,H,W)` uint8 torch 张量）取每个实例的
二值掩膜，算 `[area, aspect, θ]`。退化情况（像素 <4、接近各向同性导致朝向无意义）返回 `None`，
此时 `_measurement()` 会退回用 bbox 面积 × 0.7 做近似，保证滤波器始终有合法观测。

实测：9.mp4 首帧 **65/65** 个检测都成功拿到真实掩膜几何（样例：area=3762, r=1.70, θ=−0.12）。

## 三、⭐ 三个必须记住的踩坑（都已修）

### 坑 1：`lost_stracks` 无上限 → 轨迹被"诈尸"

**现象**：轨迹 #63 只有 30 个真实帧，却横跨 0→712 帧（gap=683）。

**根因**：`update()` 的收尾里**只把新丢失的轨迹 append 进 `lost_stracks`，从来没有清理**。
于是早期丢失的轨迹永远留在匹配池里，几百帧后被一个毫不相干的目标重新匹配上。

**修法**：按 `max_frames_lost`（= `track_buffer`）淘汰，并给 `removed_stracks` 加上上限。

```python
for t in self.lost_stracks:
    if self.frame_id - t.end_frame > self.max_frames_lost:
        t.mark_removed(); removed.append(t)
```

> ⚠️ 但 `track_buffer` 默认只有 **30**，配上淘汰逻辑后变得**过于激进**：
> 轨迹数从 89 暴涨到 **554**，真断裂 206 处、缝合 98 次。
> **必须同时把 `track_buffer` 提到 90**（与 fasttrack 基线一致）才合理。

### 坑 2：论文的 IoU 0.3 不能照搬到"融合代价"上

论文消融说 IoU 阈值 **0.3 优于 0.5**（IDSW 14.8 vs 23.4），结论是"匹配条件太严会加剧身份碎片化"。

但它测的是**纯掩膜 IoU** 代价。本实现的门限卡在 **IoU 距离与形状距离的加权融合值**上 ——
同一个 0.3 作用在融合代价上，**实际等同于一扇比原意紧得多的门**。

**结果**：用 0.3 时轨迹 89 条、真断裂 7 处；改成 **0.70** 后变成 **80 条、0 断裂**，
`stitch_tracks` 报告"**无需缝合**"。

> **教训**：外部论文的阈值只有当**代价函数的定义与量纲一致**时才可直接借用。

### 坑 3：`track_segment.py` 命中旧缓存

第一次重跑 9.mp4 时，脚本打印 `[pass 1] 命中缓存 shape_9_track_pass1.pkl` ——
**代码改了但结果没变**。必须手动删/改名 pkl 才会真正重算。

## 四、9.mp4 评测结果

### 4.1 最终对比（同检测、同 imgsz、同 conf，仅关联算法不同）

| 指标 | fasttrack (buffer 90) | **shape 7D (buffer 90, gate 0.70)** |
|---|---|---|
| 轨迹数 | 80 | **80** |
| 编号占用 | 80 | **80** |
| 真断裂 | 0 | **0** |
| 缝合动作 | 0 | **0** |
| 缺失段 | **31** | 34 |
| 最长缺失 | **18 帧** | 59 帧 |
| 同类像素重叠超标 | 0 | 0 |
| 面积跳变 | 1 | 1 |
| 形状突变 | 0 | 0 |

**结论：7D 跟踪器在一次性指标上与 fasttrack 打平，但在"最长缺失"上明显更差（59 vs 18 帧）。**

### 4.2 差在哪里（已定位到具体轨迹）

| 轨迹 | fasttrack gap | shape 7D gap |
|---|---|---|
| #6 | — | **71** |
| #62 | — | **59** |
| #7 | 28 | 10 |
| 合计 gap>50 的轨迹 | **0 条** | **2 条** |

两条出问题的轨迹都**从第 0 帧就存在**，且都是 rider —— 起点处密集人群，
说明形状门限（0.70）在密集簇里仍偏紧，导致短暂漏配后靠 coasting 硬撑，拉长了缺失。

### 4.3 消融：形状项到底贡献了多少？

把 `shape_weight` 归零（等价于"只用 IoU + 分数，但状态仍是 7D"），其余配置不变：

| 配置 | 原始实例 | 去重丢弃 | 轨迹数 | 缝合 | 短轨迹过滤 |
|---|---|---|---|---|---|
| `shape_weight=0.0` | 58072 | 0 | 82 | 无需缝合 | 1 条 (<5 帧) |
| `shape_weight=0.35` | 58072 | 0 | **80** | 无需缝合 | 0 |

**读法**：形状项在 9.mp4 上的净效果是 **少 2 条碎片轨迹、省掉 1 次短轨迹过滤**，
量级很小 —— 因为 fasttrack 的 IoU 关联本来就已接近饱和（0 断裂）。
这也从侧面说明：**当前瓶颈在检测质量的瞬时闪断，而不是关联算法的判别力**。
形状项真正的用武之地应当在"检测被遮挡掉一段时间后重新出现"的场景，
而 9.mp4 里这类情况被 fasttrack 的 coasting 已经扛住了。

## 五、要不要"多跟踪器融合"？—— 结论：**当前不需要**

用户问了这个问题，基于实测数据给出判断：

### 5.1 为什么不建议融合

1. **没有可融合的互补性。** 融合的价值来自"各路在不同场景下各有胜负"。
   实测 7D 与 fasttrack 在**同一个视频上打平**（80/80/0/0），唯一差异是 7D 更差。
   两个高度相关、且一个全面不优于另一个的跟踪器，融合只会把强的一方的结果拉向弱的一方。

2. **融合的代价很实在。** 真实的跟踪器融合需要跑 N 遍推理或维护 N 套状态，
   要么 N 倍算力（当前 pass1 已 10.5fps），要么复杂的在线仲裁。
   在收益为负的前提下，这笔开销不划算。

3. **本项目已有更便宜的"融合"在起作用。** `track_segment.py` 已经做了离线轨迹缝合
   （`stitch_tracks`，位置外推 + 残差门限），实测在新模型下**缝合动作为 0** ——
   说明检测质量已经足够好，缝合层甚至没机会发挥。再叠一层跟踪器融合属于重复建设。

### 5.2 什么情况下再考虑融合

| 触发条件 | 建议做法 |
|---|---|
| 换**黑边很宽**的源视频（如 1~8.mp4 的 2560×1440）后 7D 反超 fasttrack | 那就直接用 7D，仍然不需要融合 |
| 发现**某些视频 fasttrack 好、某些 7D 好** | 按视频选型（单跟踪器），而不是逐帧融合 |
| 需要**可解释的仲裁**且算力有余 | 才考虑「IoU 一致性仲裁」等轻量融合 |

### 5.3 更值得先做的（比融合性价比高）

1. **把 `shape_iou_thresh` 从 0.70 往下调**（如 0.60）再测 —— 直接针对 §4.2 定位到的问题；
2. **开 `with_reid: True` + `model: auto`** —— 零额外模型，官方说明就是为跨遮挡匹配设计的；
3. **给 `track_segment.py` 加双阈值滞回**（`appear_conf` 高 / `persist_conf` 低），
   与已有缝合互补，成本极低；
4. 若确实要提升 7D 的上限，**在训练侧加 `copy_paste` / `cutmix` 遮挡增强**，
   从源头减少掩膜闪断 —— 这比在跟踪层做任何融合都更根本。
